# Архитектура — как всё устроено

Обзор того, что происходит внутри сервиса: как разделены слои, как живут потоки,
как обрабатывается один запрос, что происходит с ридером и с файлом.

## Общая картина

```
        HTTP-запрос
             │
             ▼
   ┌───────────────────────┐         ┌──────────────────────────────┐
   │  app.py (event loop)  │         │  ocr.py (поток-воркер)        │
   │                       │         │                                │
   │  принять файл         │  submit │   очередь запросов             │
   │  сохранить на диск  ──┼────────▶│      │                         │
   │  положить в очередь   │         │      ▼                         │
   │  ждать future ◀───────┼─────────┼── инференс EasyOCR             │
   │  вернуть JSON         │  result │      (единолично владеет ридером)│
   └───────────────────────┘         └──────────────────────────────┘
             ▲                                     │
             │                                     ▼
        HTTP-ответ                        выгрузка ридера по простою
```

Два потока внутри одного процесса:

- **Поток event loop (FastAPI/uvicorn)** — принимает HTTP, сохраняет загрузку на
  диск, кладёт задачу в очередь и ждёт результат, не блокируя другие запросы.
- **Поток-воркер (`OcrWorker`)** — единолично владеет ридером EasyOCR, берёт
  задачи из очереди по одной и выполняет распознавание.

Процесс запускается с `--workers 1` — это **принципиально**: несколько uvicorn-
воркеров означали бы несколько копий ридера в RAM, и вся экономия памяти
пропала бы.

## Почему один воркер, а не пул

Инференс на CPU по своей сути последовательный (torch параллелит внутри по
`OMP_NUM_THREADS`). Гнать несколько распознаваний параллельно смысла нет — они
только конкурировали бы за те же ядра.

Отсюда дизайн: **все запросы в одну очередь, обрабатывает один поток**. Приятный
побочный эффект — ридер живёт только внутри воркера, к нему больше никто не
обращается, поэтому блокировки для защиты от гонок не нужны. Состояние
(`_reader`, `_last_used`) меняется и читается только из потока воркера.

Исключение — флаг «ридер загружен»: его читает `GET /health` из другого потока.
Поэтому это не обычный `bool`, а `threading.Event` (`_loaded`) — потокобезопасный.
`queue_size` тоже читается из HTTP-потока, но `queue.Queue` потокобезопасна сама.

## Мост между потоками: Queue + Future

Связь двух потоков — на двух примитивах стандартной библиотеки:

- **`queue.Queue`** — потокобезопасная очередь задач. HTTP-поток кладёт (`put`),
  воркер забирает (`get`). Очередь **без ограничения по размеру**: под наплывом
  запросы ждут своей очереди, а не получают отказ.
- **`concurrent.futures.Future`** — на каждый запрос создаётся `Future`. HTTP-
  поток кладёт в очередь задачу вместе с этим future и ждёт его; воркер по
  завершении распознавания кладёт в future результат (`set_result`) или ошибку
  (`set_exception`). Это и разбудит ожидающий HTTP-поток.

Задача — это dataclass `_Job(file_path, future)` (см.
[dataclasses.md#_job](dataclasses.md#_job)).

На стороне event loop future синхронной библиотеки оборачивается в awaitable
через `asyncio.wrap_future`, поэтому ожидание результата **не блокирует** event
loop — другие запросы в это время обрабатываются.

## Путь запроса

`POST /ocr`, шаг за шагом (`app.py`):

1. **Проверка расширения.** Расширение файла сверяется с `settings.accepted_exts`.
   Не входит в список → `415`.
2. **Сохранение на диск.** Файл потоково (`shutil.copyfileobj`, не весь в RAM)
   сохраняется во временную папку `TMP_DIR` под уникальным именем. Сама запись
   вынесена в отдельный поток (`asyncio.to_thread`), чтобы синхронное
   копирование большой загрузки не блокировало event loop. Сервис файл **не
   хранит**: он удаляется сразу после обработки (см. ниже).
3. **Постановка в очередь.** `worker.submit(file_path)` создаёт `Future`, кладёт
   `_Job` в очередь и сразу возвращает future.
4. **Ожидание.** `asyncio.wait_for(asyncio.wrap_future(future), timeout=REQUEST_TIMEOUT)`.
   Результат не пришёл за таймаут → `504`. Инференс бросил исключение → `500`.
5. **Ответ.** Список текстов страниц склеивается через `PAGE_SEPARATOR` в общий
   `text`; `OcrResponse(langs, pages, text, page_texts)` → JSON.

Всё, что связано с ридером, — на стороне воркера (`ocr.py`):

1. `_run` в цикле берёт задачу из очереди, спя на `get` до истечения простоя.
2. `_ensure_loaded` поднимает ридер, если он ещё не в RAM (ниже).
3. `_ocr` загружает страницы картинками и по одной гоняет через EasyOCR (ниже).
4. Результат кладётся в future задачи; ошибка тоже (`set_exception`), с полным
   traceback в лог (`log.exception`).
5. В `finally` временный файл удаляется. Удаляет **именно воркер**, а не
   HTTP-слой: при `504` HTTP-слой перестаёт ждать результат, но файл всё ещё
   нужен воркеру, пока тот не дочитает его в `_ocr`. Ошибка удаления только
   логируется — падать из-за неё смысла нет.

## Жизненный цикл ридера (lazy load + выгрузка по простою)

Ридер **не грузится на старте контейнера**. Это осознанный компромисс память/
латентность:

- **Cold start.** Первый запрос (или первый после выгрузки) вызывает
  `_ensure_loaded` → `easyocr.Reader(langs, gpu=False, model_storage_directory=...)`
  (жёстко CPU). Занимает несколько секунд. Если моделей ещё нет в кеше
  (`EASYOCR_MODULE_PATH`), EasyOCR дополнительно скачает их — поэтому есть шаг
  `prepare`, прогревающий кеш заранее.
- **Выгрузка по простою.** Пока ридер в RAM, воркер спит на `queue.get` не
  бесконечно, а ровно до момента истечения простоя: таймаут = `IDLE_TTL` минус
  время с последнего использования (`_idle_timeout`). Не пришло задачи за это
  время — `get` бросает `Empty`, вызывается `_unload_if_idle`, и раз простой
  действительно истёк — ридер сбрасывается (`_reader = None`), флаг снимается,
  вызывается `gc.collect()`. Так воркер просыпается **один раз, точно в срок**, а
  не поллит по фиксированному интервалу. Когда ридер уже выгружен, таймаут равен
  `None` — воркер спит до следующей задачи вообще без пробуждений.
- **Повторный подъём.** Следующий запрос снова проходит через `_ensure_loaded`.

`_last_used` обновляется дважды в `_process` — до и после инференса, потому что
сам инференс (многостраничный PDF) может идти долго, и не хочется, чтобы ридер
посчитался «простаивающим» прямо во время работы.

### Что реально происходит с памятью

При выгрузке объект ридера отпускается (`_reader = None`) и вызывается
`gc.collect()`. Крупные аллокации моделей в большинстве случаев возвращаются ОС.
Остаётся базовый «хвост» процесса (интерпретатор + torch + библиотеки). То есть
основная память освобождается, но контейнер не падает в ноль.

## Распознавание

`_ocr` состоит из двух шагов: получить страницы картинками и прогнать каждую через
EasyOCR.

### Страницы: картинка и PDF

`_load_images` приводит вход к списку numpy-картинок (RGB): картинка — одна
страница; PDF рендерится постранично через **pypdfium2** с масштабом
`PDF_DPI / 72`. pypdfium2 — чистый Python-биндинг pdfium, системный **poppler не
нужен**. Так `_ocr` дальше работает единообразно, не различая картинку и PDF.

### Инференс EasyOCR

`_recognize` зовёт `reader.readtext(image, detail=1, paragraph=PARAGRAPH)`. EasyOCR
делает детекцию текстовых областей и распознавание строк; возвращает список
результатов, где текст лежит на позиции `[1]` (и в режиме `paragraph`, и без него).
Строки склеиваются через перенос в текст страницы.

Это распознавание **строк** (детекция + recognition), без layout-разбора документа
(колонки, таблицы как структура, порядок чтения сложной вёрстки). Для сканов, фото
и простых документов этого достаточно; сложную вёрстку EasyOCR соберёт как поток
строк сверху вниз.

## Логирование

Логгер `ocr-svc` (`config.py`) пишет в **stderr** (12-factor). В докере это
подхватывает `docker compose logs`. Отдельного файла логов нет.

Значимые события: подъём ридера и время загрузки, выгрузка по простою, полный
traceback упавшего инференса (`log.exception`).

## Конфигурация

Вся конфигурация — переменные окружения, собранные в один неизменяемый `Settings`
(frozen dataclass) через `Settings.from_env()`. Единственный экземпляр `settings`
импортируют остальные модули. Поля, дефолты и соответствие env-переменным — в
[dataclasses.md#settings](dataclasses.md#settings) и в корневом README (таблица
настроек).

Число потоков CPU для torch фиксируется один раз при импорте `ocr.py`: если задан
`OMP_NUM_THREADS`, вызывается `torch.set_num_threads(...)`. `EASYOCR_MODULE_PATH`
(каталог кеша моделей) читает сам EasyOCR при создании ридера — в `Settings` он не
дублируется.

## Подготовка модели

Модели EasyOCR (детектор + распознаватели по языкам) EasyOCR качает сам при первом
создании `Reader` в каталог `EASYOCR_MODULE_PATH` (в compose — том `./models`) и
дальше грузит оттуда.

Скачивание происходит лениво при первом `_ensure_loaded`. Чтобы не платить за него
во время первого запроса, есть разовый шаг `download_model.py` (профиль `prepare`
в compose): он создаёт `easyocr.Reader(...)`, прогревая кеш. Переиспользует
основной образ — отдельный образ для подготовки не нужен.

Языки меняются переменной `OCR_LANGS`. Поменял — прогрей кеш заново (шаг
`prepare`) либо просто перезапусти сервис (модели скачаются лениво).
