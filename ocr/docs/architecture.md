# Архитектура — как всё устроено

Обзор того, что происходит внутри сервиса: как разделены слои, как живут потоки,
как обрабатывается один запрос, что происходит с моделью и с файлом.

## Общая картина

```
        HTTP-запрос
             │
             ▼
   ┌───────────────────────┐         ┌──────────────────────────────┐
   │  app.py (event loop)  │         │  ocr.py (поток-воркер)        │
   │                       │         │                                │
   │  принять файл         │  submit │   очередь запросов             │
   │  сохранить на диск  ──┼────────▶│      │                         │
   │  положить в очередь   │         │      ▼                         │
   │  ждать future ◀───────┼─────────┼── инференс PaddleOCR-VL (VLM)  │
   │  вернуть JSON         │  result │      (единолично владеет ей)   │
   └───────────────────────┘         └──────────────────────────────┘
             ▲                                     │
             │                                     ▼
        HTTP-ответ                        выгрузка модели по простою
```

Два потока внутри одного процесса:

- **Поток event loop (FastAPI/uvicorn)** — принимает HTTP, сохраняет загрузку на
  диск, кладёт задачу в очередь и ждёт результат, не блокируя другие запросы.
- **Поток-воркер (`OcrWorker`)** — единолично владеет моделью и процессором
  PaddleOCR-VL, берёт задачи из очереди по одной и выполняет распознавание.

Процесс запускается с `--workers 1` — это **принципиально**: несколько uvicorn-
воркеров означали бы несколько копий модели в RAM, и вся экономия памяти
пропала бы.

## Почему один воркер, а не пул

Инференс на CPU тяжёлый и по сути однопоточный (torch сам параллелит внутри по
`OMP_NUM_THREADS`). PaddleOCR-VL — VL-модель ~1B параметров: гнать несколько
распознаваний параллельно смысла нет — они только конкурировали бы за те же ядра
и память.

Отсюда дизайн: **все запросы в одну очередь, обрабатывает один поток**. Приятный
побочный эффект — модель живёт только внутри воркера, к ней больше никто не
обращается, поэтому блокировки для защиты от гонок не нужны. Состояние модели
(`_model`, `_processor`, `_last_used`) меняется и читается только из потока
воркера.

Исключение — флаг «модель загружена»: его читает `GET /health` из другого
потока. Поэтому это не обычный `bool`, а `threading.Event` (`_loaded`) —
потокобезопасный. `queue_size` тоже читается из HTTP-потока, но `queue.Queue`
потокобезопасна сама по себе.

## Мост между потоками: Queue + Future

Связь двух потоков — на двух примитивах стандартной библиотеки:

- **`queue.Queue`** — потокобезопасная очередь задач. HTTP-поток кладёт (`put`),
  воркер забирает (`get`). Очередь **без ограничения по размеру**: под наплывом
  запросы ждут своей очереди, а не получают отказ.
- **`concurrent.futures.Future`** — на каждый запрос создаётся `Future`. HTTP-
  поток кладёт в очередь задачу вместе с этим future и ждёт его; воркер по
  завершении распознавания кладёт в future результат (`set_result`) или ошибку
  (`set_exception`). Это и разбудит ожидающий HTTP-поток.

Задача — это dataclass `_Job(file_path, future)` (см.
[dataclasses.md#_job](dataclasses.md#_job)).

На стороне event loop future синхронной библиотеки оборачивается в awaitable
через `asyncio.wrap_future`, поэтому ожидание результата **не блокирует** event
loop — другие запросы в это время обрабатываются.

## Путь запроса

`POST /ocr`, шаг за шагом (`app.py`):

1. **Проверка расширения.** Расширение файла сверяется с `settings.accepted_exts`.
   Не входит в список → `415`.
2. **Сохранение на диск.** Файл потоково (`shutil.copyfileobj`, не весь в RAM)
   сохраняется во временную папку `TMP_DIR` под уникальным именем. Сама запись
   вынесена в отдельный поток (`asyncio.to_thread`), чтобы синхронное
   копирование большой загрузки не блокировало event loop. Сервис файл **не
   хранит**: он удаляется сразу после обработки (см. ниже).
3. **Постановка в очередь.** `worker.submit(file_path)` создаёт `Future`, кладёт
   `_Job` в очередь и сразу возвращает future.
4. **Ожидание.** `asyncio.wait_for(asyncio.wrap_future(future), timeout=REQUEST_TIMEOUT)`.
   Результат не пришёл за таймаут → `504`. Инференс бросил исключение → `500`.
5. **Ответ.** Список текстов страниц склеивается через `PAGE_SEPARATOR` в общий
   `text`; `OcrResponse(model, pages, text, page_texts)` → JSON.

Всё, что связано с моделью, — на стороне воркера (`ocr.py`):

1. `_run` в цикле берёт задачу из очереди, спя на `get` до истечения простоя.
2. `_ensure_loaded` поднимает модель и процессор, если их ещё нет в RAM (ниже).
3. `_ocr` загружает страницы картинками и по одной гоняет через VLM (ниже).
4. Результат кладётся в future задачи; ошибка тоже (`set_exception`), с полным
   traceback в лог (`log.exception`).
5. В `finally` временный файл удаляется. Удаляет **именно воркер**, а не
   HTTP-слой: при `504` HTTP-слой перестаёт ждать результат, но файл всё ещё
   нужен воркеру, пока тот не дочитает его в `_ocr`. Ошибка удаления только
   логируется — падать из-за неё смысла нет.

## Жизненный цикл модели (lazy load + выгрузка по простою)

Модель **не грузится на старте контейнера**. Это осознанный компромисс память/
латентность:

- **Cold start.** Первый запрос (или первый после выгрузки) вызывает
  `_ensure_loaded`: загружаются веса (`AutoModelForImageTextToText` или
  `AutoModelForCausalLM` — см. ниже) и `AutoProcessor`, обе с
  `trust_remote_code=True`, модель переносится на `DEVICE` и в `.eval()`. Если
  весов ещё нет в кеше (`HF_HOME`), transformers дополнительно скачает их —
  поэтому есть шаг `prepare`, прогревающий кеш заранее.
- **Выгрузка по простою.** Пока модель в RAM, воркер спит на `queue.get` не
  бесконечно, а ровно до момента истечения простоя: таймаут = `IDLE_TTL` минус
  время с последнего использования (`_idle_timeout`). Не пришло задачи за это
  время — `get` бросает `Empty`, вызывается `_unload_if_idle`, и раз простой
  действительно истёк — модель и процессор сбрасываются (`= None`), флаг
  снимается, вызывается `gc.collect()`. Так воркер просыпается **один раз, точно
  в срок**, а не поллит по фиксированному интервалу. Когда модель уже выгружена,
  таймаут равен `None` — воркер спит до следующей задачи вообще без пробуждений.
- **Повторный подъём.** Следующий запрос снова проходит через `_ensure_loaded`.

`_last_used` обновляется дважды в `_process` — до и после инференса, потому что
сам инференс может идти долго (особенно многостраничный PDF), и не хочется, чтобы
модель посчиталась «простаивающей» прямо во время работы.

### Выбор Auto-класса

Разные версии PaddleOCR-VL зарегистрированы под разные классы transformers:
базовая — под causal-lm, новые (1.6) — под image-text-to-text. `_load_model`
смотрит на `MODEL_CLASS`: при `auto` пробует `AutoModelForImageTextToText`, а при
неудаче откатывается на `AutoModelForCausalLM`; значения `causal_lm` /
`image_text_to_text` форсируют конкретный класс.

### Что реально происходит с памятью

При выгрузке объекты модели и процессора отпускаются (`= None`) и вызывается
`gc.collect()`. Крупные аллокации весов в большинстве случаев возвращаются ОС.
Остаётся базовый «хвост» процесса (интерпретатор + torch + библиотеки). То есть
основная память освобождается, но контейнер не падает в ноль.

Гарантированный возврат **всей** памяти дал бы вынос инференса в отдельный
процесс-воркер (kill по таймауту, spawn по запросу) — это отдельная доработка,
пока не сделана.

## Распознавание

`_ocr` состоит из двух шагов: получить страницы картинками и прогнать каждую через
VLM.

### Страницы: картинка и PDF

`_load_images` приводит вход к списку PIL-картинок (RGB): картинка — одна
страница; PDF рендерится постранично через **pypdfium2** с масштабом
`PDF_DPI / 72`. pypdfium2 — чистый Python-биндинг pdfium, системный **poppler не
нужен**. Так `_ocr` дальше работает единообразно, не различая картинку и PDF.

### Инференс VLM

`_recognize` собирает chat-сообщение с картинкой и текстовым промптом
(`OCR_PROMPT`), прогоняет через `processor.apply_chat_template(...)` →
`model.generate(max_new_tokens=MAX_NEW_TOKENS)` под `torch.inference_mode()`. Из
выхода **отрезаются токены промпта** (`outputs[:, prompt_len:]`), чтобы в ответ не
попал сам вопрос, и оставшееся декодируется `batch_decode(skip_special_tokens=True)`.

Это **element-level** распознавание: модель читает поданную картинку целиком.
Layout-пайплайна PaddleOCR (детекция блоков, порядок чтения, таблицы как
структура) в transformers-пути нет — для сложной вёрстки результат менее
структурирован, чем в полном пайплайне `paddleocr`. Это сознательный размен ради
запуска чистой моделью на torch по имени с HuggingFace.

## Логирование

Логгер `ocr-svc` (`config.py`) пишет в **stderr** (12-factor). В докере это
подхватывает `docker compose logs`. Отдельного файла логов нет.

Значимые события: подъём модели и время загрузки, откат Auto-класса, выгрузка по
простою, полный traceback упавшего инференса (`log.exception`).

## Конфигурация

Вся конфигурация — переменные окружения, собранные в один неизменяемый `Settings`
(frozen dataclass) через `Settings.from_env()`. Единственный экземпляр `settings`
импортируют остальные модули. Поля, дефолты и соответствие env-переменным — в
[dataclasses.md#settings](dataclasses.md#settings) и в корневом README (таблица
настроек).

Число потоков CPU для torch фиксируется один раз при импорте `ocr.py`: если задан
`OMP_NUM_THREADS`, вызывается `torch.set_num_threads(...)`. `HF_HOME` (кеш весов)
и `HF_TOKEN` (токен доступа HuggingFace для приватных/gated-моделей и снятия
лимитов загрузки) читает сам huggingface_hub из окружения — в `Settings` они не
дублируются, код менять не нужно.

## Подготовка модели

Веса и процессор PaddleOCR-VL лежат на HuggingFace. `transformers` качает их по
имени модели (`MODEL_NAME`) в кеш HuggingFace (`HF_HOME`, в compose — том
`./models`) и дальше грузит оттуда.

Скачивание происходит лениво при первом `_ensure_loaded`. Чтобы не платить за него
во время первого запроса, есть разовый шаг `download_model.py` (профиль `prepare`
в compose): он вызывает `snapshot_download(MODEL_NAME)`, стягивая весь репозиторий
модели (веса + конфиг + кастомный код + токенизатор) в кеш. Переиспользует основной
образ — отдельный образ для подготовки не нужен.

Модель меняется одной переменной `MODEL_NAME`. Поменял — прогрей кеш заново (шаг
`prepare`) либо просто перезапусти сервис (веса скачаются лениво).
