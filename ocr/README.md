# PaddleOCR-VL OCR — standalone-сервис (transformers/torch, CPU, Docker)

HTTP-сервис распознавания текста на изображениях и в PDF на модели
**PaddleOCR-VL**, запускаемой через **HuggingFace transformers (torch)**.
Работает **только на CPU**, запросы обрабатываются по очереди одним воркером, а
модель **выгружается из RAM при простое** и поднимается обратно по запросу.
Принимает картинки и PDF. Имя модели — в `.env`, всё запускается через Docker.

Сделан по образцу соседних сервисов `../asr-gigaam` и `../embedder` (та же
архитектура: очередь + поток-воркер + ленивая загрузка/выгрузка модели).

> **Важно про transformers-путь.** Модель гоняется как VLM: картинка + промпт
> (`OCR:`) → текст. Layout-пайплайна PaddleOCR (детекция блоков, порядок чтения,
> таблицы как структура) в этом пути **нет** — распознаётся картинка целиком
> (element-level). Для простых сканов/страниц это ок; для сложной вёрстки
> результат менее структурирован, чем в полном пайплайне `paddleocr`. PDF
> рендерится в картинки постранично через `pypdfium2` (системный poppler не
> нужен).

## Быстрый старт

```bash
# 1. настройки
cp .env.example .env        # при желании поправь MODEL_NAME, PORT, OMP_NUM_THREADS

# 2. разовое скачивание весов с HuggingFace в кеш (./models)
docker compose --profile prepare run --rm prepare

# 3. поднять сервис
docker compose up -d --build
```

Шаг 2 объявлен под профилем `prepare`, поэтому обычным `docker compose up` он не
поднимается — запускается только явной командой (разово, `run --rm`). Он лишь
прогревает кеш, чтобы сервис не качал веса во время первого запроса; можно и
пропустить — тогда веса скачаются лениво при первом `/ocr`. Шаг 3 поднимает сам
сервис `ocr`.

Проверка:

```bash
curl -F "file=@scan.pdf" http://{host}:{port}/ocr
# {"model":"PaddlePaddle/PaddleOCR-VL","pages":2,"text":"...","page_texts":["...","..."]}

curl http://{host}:{port}/health
# {"status":"ok","model":"PaddlePaddle/PaddleOCR-VL","loaded":false,"queue":0}
```

## API

Интерактивная документация поднимается вместе с сервисом:

- **Swagger UI** — `http://localhost:8002/docs`
- **ReDoc** — `http://localhost:8002/redoc`
- **OpenAPI-схема** — `http://localhost:8002/openapi.json`

Типы тел ответов описаны dataclass'ами в `schemas.py` и автоматически попадают
в OpenAPI-схему.

### `POST /ocr`

Распознать текст на изображении или в PDF.

- **Тело:** `multipart/form-data`, поле `file` — изображение или PDF.
- **Принимаемые форматы:** `png`, `jpg`, `jpeg`, `tiff`, `tif`, `bmp`, `webp`,
  `pdf`.
- **Ответ `200`** (`OcrResponse`):

  ```json
  {
    "model": "PaddlePaddle/PaddleOCR-VL",
    "pages": 2,
    "text": "страница 1\n\n---\n\nстраница 2",
    "page_texts": ["страница 1", "страница 2"]
  }
  ```

  | Поле         | Тип         | Значение                                         |
  |--------------|-------------|--------------------------------------------------|
  | `model`      | string      | имя HF-модели (`MODEL_NAME`)                     |
  | `pages`      | int         | число распознанных страниц                       |
  | `text`       | string      | весь текст, страницы через `PAGE_SEPARATOR`      |
  | `page_texts` | list[string]| текст по одной строке на страницу                |

- **Ошибки:**

  | Код   | Когда                                                        |
  |-------|--------------------------------------------------------------|
  | `415` | неподдерживаемое расширение файла                            |
  | `422` | не передан файл (валидация запроса, добавляет FastAPI)       |
  | `500` | инференс упал                                                |
  | `504` | результат не пришёл за `REQUEST_TIMEOUT`                      |

  ```bash
  curl -F "file=@scan.png" http://localhost:8002/ocr
  ```

### `GET /health`

Состояние сервиса и воркера. Модель не поднимает — годится как healthcheck.

- **Ответ `200`** (`HealthResponse`):

  ```json
  { "status": "ok", "model": "PaddlePaddle/PaddleOCR-VL", "loaded": false, "queue": 0 }
  ```

  | Поле     | Тип    | Значение                                              |
  |----------|--------|-------------------------------------------------------|
  | `status` | string | всегда `"ok"`, если процесс отвечает                  |
  | `model`  | string | имя HF-модели (`MODEL_NAME`)                          |
  | `loaded` | bool   | загружена ли модель в RAM прямо сейчас                |
  | `queue`  | int    | сколько запросов ждёт в очереди воркера               |

## Настройки (.env)

| Переменная         | По умолчанию                  | Назначение                                      |
|--------------------|-------------------------------|-------------------------------------------------|
| `MODEL_NAME`       | `PaddlePaddle/PaddleOCR-VL`   | имя HF-модели PaddleOCR-VL для transformers     |
| `MODEL_CLASS`      | `auto`                        | Auto-класс загрузки (`auto`/`causal_lm`/`image_text_to_text`) |
| `DEVICE`           | `cpu`                         | устройство инференса                            |
| `TORCH_DTYPE`      | `float32`                     | тип весов (на CPU — `float32`)                  |
| `OCR_PROMPT`       | `OCR:`                        | промпт задачи VLM                               |
| `MAX_NEW_TOKENS`   | `2048`                        | потолок генерации на страницу                   |
| `PDF_DPI`          | `150`                         | DPI рендера страниц PDF перед OCR               |
| `HF_HOME`          | `/app/models`                 | кеш HuggingFace с весами (том `./models`)       |
| `HF_TOKEN`         | *(пусто)*                     | токен HuggingFace для приватных/gated-моделей и снятия лимитов загрузки |
| `TMP_DIR`          | `/app/tmp`                    | временная папка для файлов; удаляются сразу после распознавания |
| `IDLE_TTL`         | `300`                         | сек простоя до выгрузки модели из RAM           |
| `REQUEST_TIMEOUT`  | `600`                         | макс. ожидание результата, сек; дольше — `504`  |
| `PAGE_SEPARATOR`   | `\n\n---\n\n`                 | разделитель страниц в общем `text` (берётся из env литерально) |
| `OMP_NUM_THREADS`  | `4`                           | потоки CPU для torch (≈ число физ. ядер)        |
| `PORT`             | `8002`                        | порт на хосте                                   |

> Модель меняется одной переменной `MODEL_NAME`. Разные версии зарегистрированы
> под разные Auto-классы (базовая — causal-lm, 1.6 — image-text-to-text); `auto`
> подберёт сам, либо задай `MODEL_CLASS` явно. Поменял модель? Прогони шаг 2 (или
> просто перезапусти сервис — веса скачаются лениво), затем `docker compose up -d`.

## Как это работает

- Запросы складываются в очередь (без ограничения по размеру); обрабатывает их
  один поток-воркер, который единолично владеет моделью. Параллельный инференс
  на CPU смысла не имеет, а единоличное владение избавляет от блокировок и гонок.
- Модель не грузится при старте контейнера. Первый запрос поднимает её в RAM
  (cold start; если весов ещё нет в кеше — добавится время на скачивание с
  HuggingFace, поэтому есть шаг `prepare`).
- Инференс — на **PaddleOCR-VL** через `transformers` поверх `torch` (CPU):
  `AutoModelForImageTextToText`/`AutoModelForCausalLM` + `AutoProcessor` с
  `trust_remote_code=True`. Каждая страница подаётся картинкой с промптом
  (`OCR_PROMPT`), модель генерирует текст, из вывода отрезаются токены промпта.
- PDF рендерится в картинки постранично через `pypdfium2` (DPI = `PDF_DPI`),
  каждая страница распознаётся отдельно; тексты собираются в `page_texts`.
- Тот же воркер выгружает модель из RAM, если запросов не было дольше
  `IDLE_TTL`. Следующий запрос поднимает её заново.
- Результат не пришёл за `REQUEST_TIMEOUT` → `504`.
- Загруженный файл пишется во временную папку (`TMP_DIR`) и **удаляется сразу
  после обработки** — успешной или нет. Сервис ничего не хранит; хранение и БД
  живут в отдельном сервисе. Удаляет файл воркер (не HTTP-слой): при `504`
  запрос перестаёт ждать, но файл ещё нужен воркеру до конца распознавания.

`--workers 1` в `Dockerfile` — принципиально: иначе каждый воркер держит свою
копию модели в RAM, и экономия памяти теряется.

> **Про скорость.** PaddleOCR-VL — VL-модель ~1B параметров. На CPU генерация
> медленная (минуты на страницу при большом `MAX_NEW_TOKENS`), особенно
> многостраничный PDF — отсюда большой `REQUEST_TIMEOUT`. Если нужен throughput —
> вынести инференс на GPU (`DEVICE=cuda`, `TORCH_DTYPE=bfloat16`) или на vLLM;
> здесь сознательно всё на CPU ради простоты и переносимости.

## Про выгрузку из RAM — что реально происходит

При простое сервис отпускает модель и процессор (`= None`) и зовёт `gc.collect()`.
Крупные аллокации весов в большинстве случаев возвращаются ОС; остаётся базовый
«хвост» процесса (интерпретатор + torch + библиотеки). То есть основная память
освобождается, но контейнер не падает в ноль.

Хочешь **гарантированный** возврат всей памяти при простое — инференс выносится в
процесс-воркер, который убивается по таймауту и спавнится по запросу. Это +немного
кода; скажи — допишу.

## Локальный запуск без Docker (опционально)

```bash
# torch ставится CPU-only отдельным индексом
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt python-dotenv
# веса скачаются с HuggingFace в кеш (HF_HOME) при первом запросе
uvicorn app:app --host 0.0.0.0 --port 8002 --workers 1
```
