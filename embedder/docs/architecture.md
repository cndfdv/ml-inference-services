# Архитектура — как всё устроено

Обзор того, что происходит внутри сервиса: как разделены слои, как живут потоки,
как обрабатывается один запрос, что происходит с моделью.

## Общая картина

```
        HTTP-запрос
             │
             ▼
   ┌───────────────────────┐         ┌──────────────────────────────┐
   │  app.py (event loop)  │         │  embedder.py (поток-воркер)   │
   │                       │         │                                │
   │  принять JSON         │  submit │   очередь запросов             │
   │  проверить лимит    ──┼────────▶│      │                         │
   │  положить в очередь   │         │      ▼                         │
   │  ждать future ◀───────┼─────────┼── инференс на модели           │
   │  вернуть JSON         │  result │      (единолично владеет ей)   │
   └───────────────────────┘         └──────────────────────────────┘
             ▲                                     │
             │                                     ▼
        HTTP-ответ                        выгрузка модели по простою
```

Два потока внутри одного процесса:

- **Поток event loop (FastAPI/uvicorn)** — принимает HTTP, валидирует тело,
  кладёт задачу в очередь и ждёт результат, не блокируя другие запросы.
- **Поток-воркер (`EmbedderWorker`)** — единолично владеет моделью, берёт задачи
  из очереди по одной и выполняет инференс (кодирование текстов в векторы).

Процесс запускается с `--workers 1` — это **принципиально**: несколько uvicorn-
воркеров означали бы несколько копий модели в RAM, и вся экономия памяти
пропала бы.

## Почему один воркер, а не пул

Инференс на CPU тяжёлый и по сути однопоточный (torch сам параллелит внутри по
`OMP_NUM_THREADS` через BLAS/OpenMP). Гнать несколько кодирований параллельно
смысла нет — они только конкурировали бы за те же ядра и мешали друг другу.

Отсюда дизайн: **все запросы в одну очередь, обрабатывает один поток**. Приятный
побочный эффект — модель живёт только внутри воркера, к ней больше никто не
обращается, поэтому блокировки для защиты от гонок не нужны. Состояние модели
(`_model`, `_last_used`) меняется и читается только из потока воркера.

Исключение — флаг «модель загружена»: его читает `GET /health` из другого
потока. Поэтому это не обычный `bool`, а `threading.Event` (`_loaded`) —
потокобезопасный. `queue_size` тоже читается из HTTP-потока, но `queue.Queue`
потокобезопасна сама по себе.

## Мост между потоками: Queue + Future

Связь двух потоков — на двух примитивах стандартной библиотеки:

- **`queue.Queue`** — потокобезопасная очередь задач. HTTP-поток кладёт (`put`),
  воркер забирает (`get`). Очередь **без ограничения по размеру**: под наплывом
  запросы ждут своей очереди, а не получают отказ.
- **`concurrent.futures.Future`** — на каждый запрос создаётся `Future`. HTTP-
  поток кладёт в очередь задачу вместе с этим future и ждёт его; воркер по
  завершении инференса кладёт в future результат (`set_result`) или ошибку
  (`set_exception`). Это и разбудит ожидающий HTTP-поток.

Задача — это dataclass `_Job(texts, future)` (см.
[dataclasses.md#_job](dataclasses.md#_job)).

На стороне event loop future синхронной библиотеки оборачивается в awaitable
через `asyncio.wrap_future`, поэтому ожидание результата **не блокирует** event
loop — другие запросы в это время обрабатываются.

## Путь запроса

`POST /embed`, шаг за шагом (`app.py`):

1. **Валидация тела.** FastAPI разбирает JSON в `EmbedRequest` (pydantic): поле
   `texts` — непустой список строк. Пустой список → `422` (валидация pydantic).
2. **Проверка лимита.** `len(texts) > settings.max_texts` → `422` (защита от OOM
   на слишком больших батчах).
3. **Постановка в очередь.** `worker.submit(texts)` создаёт `Future`, кладёт
   `_Job` в очередь и сразу возвращает future.
4. **Ожидание.** `asyncio.wait_for(asyncio.wrap_future(future), timeout=REQUEST_TIMEOUT)`.
   Результат не пришёл за таймаут → `504`. Инференс бросил исключение → `500`.
5. **Ответ.** `EmbedResponse(model, dim, count, embeddings)` → JSON.

Всё, что связано с моделью, — на стороне воркера (`embedder.py`):

1. `_run` в цикле берёт задачу из очереди, спя на `get` до истечения простоя.
2. `_ensure_loaded` поднимает модель, если она ещё не в RAM (см. ниже).
3. `_embed` добавляет опциональный префикс и гоняет `model.encode` (см. ниже).
4. Результат (список векторов) кладётся в future задачи; ошибка тоже
   (`set_exception`), с полным traceback в лог (`log.exception`).

В отличие от ASR-сервиса, здесь **нет временных файлов**: вход — текст в теле
запроса, на диск ничего не пишется, чистить нечего.

## Жизненный цикл модели (lazy load + выгрузка по простою)

Модель **не грузится на старте контейнера**. Это осознанный компромисс память/
латентность:

- **Cold start.** Первый запрос (или первый после выгрузки) вызывает
  `_ensure_loaded` → `SentenceTransformer(model_name, device="cpu")` (жёстко CPU).
  Занимает несколько секунд. Если модели ещё нет в кеше HuggingFace (`HF_HOME`),
  sentence-transformers дополнительно скачает её — поэтому есть шаг `prepare`,
  прогревающий кеш заранее.
- **Выгрузка по простою.** Пока модель в RAM, воркер спит на `queue.get` не
  бесконечно, а ровно до момента истечения простоя: таймаут = `IDLE_TTL` минус
  время с последнего использования (`_idle_timeout`). Не пришло задачи за это
  время — `get` бросает `Empty`, вызывается `_unload_if_idle`, и раз простой
  действительно истёк — модель сбрасывается (`_model = None`), флаг снимается,
  вызывается `gc.collect()`. Так воркер просыпается **один раз, точно в срок**, а
  не поллит по фиксированному интервалу. Когда модель уже выгружена, таймаут
  равен `None` — воркер спит до следующей задачи вообще без пробуждений.
- **Повторный подъём.** Следующий запрос снова проходит через `_ensure_loaded`.

`_last_used` обновляется дважды в `_process` — до и после инференса, потому что
сам инференс может идти долго, и не хочется, чтобы модель посчиталась
«простаивающей» прямо во время работы.

### Что реально происходит с памятью

При выгрузке модель освобождается (`_model = None`) и вызывается `gc.collect()`.
Веса — крупные аллокации, в большинстве случаев возвращаются ОС. Остаётся базовый
«хвост» процесса (интерпретатор + torch + библиотеки, ~несколько сотен МБ). То
есть основная память освобождается, но контейнер не падает в ноль.

Гарантированный возврат **всей** памяти дал бы вынос инференса в отдельный
процесс-воркер (kill по таймауту, spawn по запросу) — это отдельная доработка,
пока не сделана.

## Кодирование текста

В `_embed` два момента стоит пояснить.

### Опциональный префикс (`EMBED_PREFIX`)

Часть моделей — **асимметричные**: они ждут короткий префикс перед текстом.
Классика — семейство `intfloat/multilingual-e5-*`: `query: ` для поисковых
запросов, `passage: ` для индексируемых документов. Без префикса качество заметно
падает. Поэтому `_embed` подставляет `settings.embed_prefix` к каждому тексту,
если он задан; пусто — тексты идут как есть. Для **симметричных** моделей
(`sergeyzh/rubert-tiny-turbo`, `all-MiniLM-L6-v2`) префикс не нужен.

Префикс — это настройка развёртывания под конкретную модель, поэтому он в `.env`,
а не зашит в код.

### Батчинг и нормализация

`model.encode` принимает список текстов и кодирует их партиями по `BATCH_SIZE`
(параметр `batch_size`) — больше батч быстрее, но выше пик памяти.
`normalize_embeddings=settings.normalize` включает L2-нормализацию векторов: с ней
косинусная близость сводится к скалярному произведению, что удобно для векторного
поиска. Результат приводится к `float32` и отдаётся обычными списками Python —
готовыми к сериализации в JSON.

## Логирование

Логгер `embedder-svc` (`config.py`) пишет в **stderr** (12-factor). В докере это
подхватывает `docker compose logs`. Отдельного файла логов нет.

Значимые события: подъём модели и время загрузки, выгрузка по простою, полный
traceback упавшего инференса (`log.exception`).

## Конфигурация

Вся конфигурация — переменные окружения, собранные в один неизменяемый `Settings`
(frozen dataclass) через `Settings.from_env()`. Единственный экземпляр `settings`
импортируют остальные модули. Поля, дефолты и соответствие env-переменным — в
[dataclasses.md#settings](dataclasses.md#settings) и в корневом README (таблица
настроек).

Число потоков CPU для torch фиксируется один раз при импорте `embedder.py`: если
задан `OMP_NUM_THREADS`, вызывается `torch.set_num_threads(...)` (torch читает
переменную и сам, но задаём явно для предсказуемости).

Часть переменных читают напрямую библиотеки, а не `Settings`: `HF_HOME` (куда
класть кеш весов) и `HF_TOKEN` (токен доступа HuggingFace для приватных/gated-
моделей и снятия лимитов загрузки) подхватывает `huggingface_hub` из окружения —
код для этого менять не нужно.

## Подготовка модели

Веса модели лежат на HuggingFace. `sentence-transformers` скачивает их по имени
модели (`MODEL_NAME`) в кеш HuggingFace (`HF_HOME`, в compose — том `./models`) и
дальше грузит оттуда.

Скачивание происходит лениво при первом `_ensure_loaded`. Чтобы не платить за него
во время первого запроса, есть разовый шаг `download_model.py` (профиль `prepare`
в compose): он просто создаёт `SentenceTransformer(MODEL_NAME)`, прогревая кеш.
Переиспользует основной образ — отдельный образ для подготовки не нужен.

Модель меняется одной переменной `MODEL_NAME` — подойдёт любая эмбеддинг-модель с
HuggingFace, совместимая с sentence-transformers. Поменял модель — прогрей кеш
заново (шаг `prepare`) либо просто перезапусти сервис (скачается лениво).
