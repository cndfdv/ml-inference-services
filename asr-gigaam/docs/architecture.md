# Архитектура — как всё устроено

Обзор того, что происходит внутри сервиса: как разделены слои, как живут потоки,
как обрабатывается один запрос, что происходит с моделью и с аудио.

## Общая картина

```
        HTTP-запрос
             │
             ▼
   ┌───────────────────────┐         ┌──────────────────────────────┐
   │  app.py (event loop)  │         │  transcriber.py (поток-воркер) │
   │                       │         │                                │
   │  принять файл         │  submit │   очередь запросов             │
   │  сохранить на диск  ──┼────────▶│      │                         │
   │  положить в очередь   │         │      ▼                         │
   │  ждать future ◀───────┼─────────┼── инференс на ONNX-модели      │
   │  вернуть JSON         │  result │      (единолично владеет ей)   │
   └───────────────────────┘         └──────────────────────────────┘
             ▲                                     │
             │                                     ▼
        HTTP-ответ                        выгрузка модели по простою
```

Два потока внутри одного процесса:

- **Поток event loop (FastAPI/uvicorn)** — принимает HTTP, сохраняет загрузку на
  диск, кладёт задачу в очередь и ждёт результат, не блокируя другие запросы.
- **Поток-воркер (`TranscriberWorker`)** — единолично владеет ONNX-моделью,
  берёт задачи из очереди по одной и выполняет инференс.

Процесс запускается с `--workers 1` — это **принципиально**: несколько uvicorn-
воркеров означали бы несколько копий модели в RAM, и вся экономия памяти
пропала бы.

## Почему один воркер, а не пул

Инференс на CPU тяжёлый и по сути однопоточный (onnxruntime сам параллелит
внутри по `OMP_NUM_THREADS`). Гнать несколько инференсов параллельно смысла нет —
они только конкурировали бы за те же ядра и мешали друг другу.

Отсюда дизайн: **все запросы в одну очередь, обрабатывает один поток**. Приятный
побочный эффект — модель живёт только внутри воркера, к ней больше никто не
обращается, поэтому блокировки для защиты от гонок не нужны. Состояние модели
(`_model`, `_last_used`) меняется и читается только из потока воркера.

Исключение — флаг «модель загружена»: его читает `GET /health` из другого
потока. Поэтому это не обычный `bool`, а `threading.Event` (`_loaded`) —
потокобезопасный. `queue_size` тоже читается из HTTP-потока, но `queue.Queue`
потокобезопасна сама по себе.

## Мост между потоками: Queue + Future

Связь двух потоков — на двух примитивах стандартной библиотеки:

- **`queue.Queue`** — потокобезопасная очередь задач. HTTP-поток кладёт (`put`),
  воркер забирает (`get`). Очередь **без ограничения по размеру**: под наплывом
  запросы ждут своей очереди, а не получают отказ.
- **`concurrent.futures.Future`** — на каждый запрос создаётся `Future`. HTTP-
  поток кладёт в очередь задачу вместе с этим future и ждёт его; воркер по
  завершении инференса кладёт в future результат (`set_result`) или ошибку
  (`set_exception`). Это и разбудит ожидающий HTTP-поток.

Задача — это dataclass `_Job(audio_path, future)` (см.
[dataclasses.md#_job](dataclasses.md#_job)).

На стороне event loop future синхронной библиотеки оборачивается в awaitable
через `asyncio.wrap_future`, поэтому ожидание результата **не блокирует** event
loop — другие запросы в это время обрабатываются.

## Путь запроса

`POST /transcribe`, шаг за шагом (`app.py`):

1. **Проверка расширения.** Расширение файла сверяется с `settings.accepted_exts`.
   Не входит в список → `415`. (Декодирует всё равно ffmpeg, но явный список
   отсекает мусорные загрузки.)
2. **Сохранение на диск.** Файл потоково (`shutil.copyfileobj`, не весь в RAM)
   сохраняется во временную папку `TMP_DIR` под уникальным именем. Сама запись
   вынесена в отдельный поток (`asyncio.to_thread`), чтобы синхронное
   копирование большой загрузки не блокировало event loop. Сервис аудио **не
   хранит**: файл удаляется сразу после обработки (см. ниже).
3. **Постановка в очередь.** `worker.submit(audio_path)` создаёт `Future`, кладёт
   `_Job` в очередь и сразу возвращает future.
4. **Ожидание.** `asyncio.wait_for(asyncio.wrap_future(future), timeout=REQUEST_TIMEOUT)`.
   Результат не пришёл за таймаут → `504`. Инференс бросил исключение → `500`.
5. **Ответ.** `TranscribeResponse(text=...)` → JSON `{"text": "..."}`.

Всё, что связано с моделью, — на стороне воркера (`transcriber.py`):

1. `_run` в цикле берёт задачу из очереди, спя на `get` до истечения простоя.
2. `_ensure_loaded` поднимает модель, если она ещё не в RAM (см. ниже).
3. `_transcribe` декодирует аудио и гоняет инференс (декод + чанковка — ниже).
4. Результат кладётся в future задачи; ошибка тоже (`set_exception`).
5. В `finally` временный файл удаляется. Удаляет **именно воркер**, а не
   HTTP-слой: при `504` HTTP-слой перестаёт ждать результат, но файл всё ещё
   нужен воркеру, пока тот не дочитает его в `_transcribe`. Ошибка удаления
   только логируется — падать из-за неё смысла нет.

## Жизненный цикл модели (lazy load + выгрузка по простою)

Модель **не грузится на старте контейнера**. Это осознанный компромисс память/
латентность:

- **Cold start.** Первый запрос (или первый после выгрузки) вызывает
  `_ensure_loaded` → `onnx_asr.load_model(model_version, providers=["CPUExecutionProvider"])`
  (жёстко CPU, чтобы onnxruntime не искал CUDA). Занимает несколько секунд. Если
  модели ещё нет в кеше HuggingFace (`HF_HOME`), onnx-asr дополнительно скачает
  её — поэтому есть шаг `prepare`, прогревающий кеш заранее.
- **Выгрузка по простою.** Пока модель в RAM, воркер спит на `queue.get` не
  бесконечно, а ровно до момента истечения простоя: таймаут = `IDLE_TTL` минус
  время с последнего использования (`_idle_timeout`). Не пришло задачи за это
  время — `get` бросает `Empty`, вызывается `_unload_if_idle`, и раз простой
  действительно истёк — модель сбрасывается (`_model = None`), флаг
  снимается, вызывается `gc.collect()`. Так воркер просыпается **один раз, точно
  в срок**, а не поллит по фиксированному интервалу. Когда модель уже выгружена,
  таймаут равен `None` — воркер спит до следующей задачи вообще без пробуждений.
- **Повторный подъём.** Следующий запрос снова проходит через `_ensure_loaded`.

`_last_used` обновляется дважды в `_process` — до и после инференса, потому что
сам инференс может идти долго, и не хочется, чтобы модель посчиталась «простаивающей»
прямо во время работы.

### Что реально происходит с памятью

При выгрузке удаляются ONNX-сессии модели и вызывается `gc.collect()`. Веса —
крупные аллокации, в большинстве случаев возвращаются ОС. Остаётся базовый
«хвост» процесса (интерпретатор + библиотеки, ~150–300 МБ). То есть основная
память освобождается, но контейнер не падает в ноль.

Гарантированный возврат **всей** памяти дал бы вынос инференса в отдельный
процесс-воркер (kill по таймауту, spawn по запросу) — это отдельная доработка,
пока не сделана.

## Декодирование аудио и чанковка

В `_transcribe` есть два неочевидных решения.

### Декод через ffmpeg, а не по пути

`recognize` в onnx-asr читает файл по пути только в формате PCM-wav — а сервис
принимает mp3/mp4/m4a и прочие контейнеры. Поэтому аудио декодируется
**самостоятельно** (`_decode_audio`) через ffmpeg, а в `recognize` отдаётся уже
готовый waveform — numpy float32, моно, 16 кГц (диапазон `[-1, 1]`, ровно то,
что ждёт onnx-asr).

Один проход ffmpeg: декодируем любой контейнер и на том же проходе применяем
цепочку фильтров `AUDIO_FILTERS` (`-af`), сразу в сырой PCM f32 на stdout,
который читаем в массив. Если `AUDIO_FILTERS` пуст — тот же ffmpeg без `-af`.
Это **аудио-предобработка**: срез гула (`highpass`), выравнивание громкости
(`dynaudnorm`/`loudnorm`), при желании шумодав (`afftdn`). Помогает на
тихой/шумной записи; на чистом аудио эффект небольшой. Осторожно с агрессивным
шумодавом — он может ухудшить распознавание. Не заменяет модель: пунктуацию даёт
`gigaam-v3-e2e-ctc`/пост-обработка, а не фильтры.

### Нарезка на окна (защита от OOM)

Память conformer-энкодера растёт **~квадратично** от длины входа. Файл на десятки
минут целиком уводит процесс в OOM (снаружи это выглядело как «Empty reply from
server» — контейнер молча перезапускался по `restart: unless-stopped`).

Решение: waveform режется на окна по `CHUNK_SEC` секунд
(`win = chunk_sec * SAMPLE_RATE`). Окна прогоняются через `recognize` (он
принимает список массивов = батч) партиями по `CHUNK_BATCH_SIZE`, результаты
склеиваются в один текст через пробел. Батчим вручную, чтобы пик памяти не рос с
числом окон (recognize паддит батч под самое длинное окно). Пик теперь ограничен
размером окна и батча, а не длиной записи. `CHUNK_SEC=0` отключает нарезку
(только для заведомо коротких файлов).

**Известное ограничение:** фиксированные окна могут обрезать слово на стыке.
onnx-asr умеет нарезку по тишине из коробки (`model.with_vad()`) — это
напрашивающийся апгрейд качества стыков, пока не подключён.

## Логирование

Логгер `gigaam-svc` (`config.py`) пишет в **stderr** (12-factor). В докере это
подхватывает `docker compose logs`. Отдельного файла логов нет.

Значимые события: подъём модели и время загрузки, выгрузка по простою, полный
traceback упавшего инференса (`log.exception`).

## Конфигурация

Вся конфигурация — переменные окружения, собранные в один неизменяемый
`Settings` (frozen dataclass) через `Settings.from_env()`. Единственный экземпляр
`settings` импортируют остальные модули. Поля, дефолты и соответствие env-
переменным — в [dataclasses.md#settings](dataclasses.md#settings) и в
корневом README (таблица настроек).

## Подготовка модели

Веса — это готовый ONNX-экспорт GigaAM, лежащий на HuggingFace (репозиторий
`istupakov/gigaam-v3-onnx`). `onnx-asr` скачивает их по имени модели
(`MODEL_VERSION`) в кеш HuggingFace (`HF_HOME`, в compose — том `./models`) и
дальше грузит оттуда. torch для этого не нужен — препроцессинг у onnx-asr свой,
на numpy/onnxruntime.

Скачивание происходит лениво при первом `_ensure_loaded`. Чтобы не платить за него
во время первого запроса, есть разовый шаг `download_model.py` (профиль `prepare`
в compose): он просто зовёт `onnx_asr.load_model(MODEL_VERSION)`, прогревая кеш.
Переиспользует основной образ — отдельный «тяжёлый» образ для подготовки больше
не нужен.

> **Почему съехали с родного экспорта gigaam.** Раньше веса тянулись библиотекой
> `gigaam` с CDN SberDevices и экспортировались в ONNX через torch. CDN закрыл
> публичный доступ к бакету (403 для всех, включая офиц. примеры), а `.ckpt` в
> открытом виде нигде не осталось. Готовый ONNX на HuggingFace + `onnx-asr`
> обходят мёртвый CDN и заодно убирают torch из рантайма.
