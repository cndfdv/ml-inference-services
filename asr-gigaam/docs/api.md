# HTTP API

Два эндпоинта: распознавание и healthcheck. Типы тел ответов описаны
dataclass'ами в `schemas.py` (см. [dataclasses.md](dataclasses.md)) и
автоматически попадают в OpenAPI-схему.

## Интерактивная документация

Поднимается вместе с сервисом (FastAPI):

- **Swagger UI** — `http://<host>:<port>/docs`
- **ReDoc** — `http://<host>:<port>/redoc`
- **OpenAPI-схема (JSON)** — `http://<host>:<port>/openapi.json`

По умолчанию порт `8000` (переопределяется `PORT` в `.env`).

## `POST /transcribe`

Распознать речь из аудиофайла.

### Запрос

- **Content-Type:** `multipart/form-data`
- **Поле `file`** — аудиофайл (обязательное).
- **Принимаемые расширения:** `wav`, `mp3`, `mp4`, `m4a`, `flac`, `ogg`, `opus`,
  `aac`, `webm`, `wma`. Декодирует ffmpeg, так что контейнер почти безразличен;
  список отсекает мусорные загрузки.

```bash
curl -F "file=@sample.wav" http://localhost:8000/transcribe
```

### Ответ `200` — `TranscribeResponse`

```json
{ "text": "распознанный текст" }
```

| Поле   | Тип    | Значение             |
|--------|--------|----------------------|
| `text` | string | Распознанный текст.  |

### Коды ошибок

| Код   | Когда | Тело |
|-------|-------|------|
| `415` | Неподдерживаемое расширение файла | `{"detail": "Неподдерживаемый формат '...'. Принимаем: ..."}` |
| `422` | Не передан файл `file` (валидация FastAPI) | стандартный `{"detail": [...]}` |
| `500` | Инференс упал | `{"detail": "<текст ошибки>"}` |
| `504` | Результат не пришёл за `REQUEST_TIMEOUT` (очередь + инференс) | `{"detail": "Время ожидания распознавания истекло"}` |

### Что важно знать

- **Обработка по очереди.** Запрос встаёт в очередь и ждёт своей очереди у
  единственного воркера. Под нагрузкой время ответа = ожидание в очереди +
  инференс. Отказа из-за переполнения нет — очередь не ограничена.
- **Cold start.** Первый запрос после старта или после простоя дольше `IDLE_TTL`
  дополнительно ждёт подъёма модели в RAM (несколько секунд).
- **Длинное аудио.** Режется на окна по `CHUNK_SEC` секунд и склеивается —
  отдельных действий от клиента не требует (детали в
  [architecture.md](architecture.md#декодирование-аудио-и-чанковка)).

## `GET /health`

Состояние сервиса и воркера. Модель **не поднимает** — безопасно дёргать как
healthcheck и мониторинг очереди.

```bash
curl http://localhost:8000/health
```

### Ответ `200` — `HealthResponse`

```json
{ "status": "ok", "model": "gigaam-v3-ctc", "loaded": false, "queue": 0 }
```

| Поле     | Тип    | Значение                                                    |
|----------|--------|-------------------------------------------------------------|
| `status` | string | Всегда `"ok"`, если процесс отвечает.                       |
| `model`  | string | Версия модели (`MODEL_VERSION`).                            |
| `loaded` | bool   | Загружена ли модель в RAM прямо сейчас.                     |
| `queue`  | int    | Сколько запросов сейчас ждёт в очереди воркера.             |

`queue` и есть «посмотреть очередь»: это её текущая длина. Списка задач с их
статусами по замыслу нет — API синхронный: клиент держит запрос открытым до
ответа, так что job ID и промежуточные статусы не нужны.

## Границы сервиса

Сервис занят одним делом — распознаванием речи — и рассчитан на работу внутри
доверенной сети, за шлюзом. Всё, что относится к периметру, намеренно живёт на
внешнем слое (reverse proxy / API-шлюз), а не здесь:

- аутентификация и авторизация;
- HTTPS (TLS) — сам процесс слушает обычный HTTP;
- CORS;
- rate limiting.
