# GigaAM ASR — standalone-сервис (ONNX, CPU, Docker)

HTTP-сервис распознавания речи на GigaAM. Модель в ONNX, работает **только на
CPU**, запросы обрабатываются по очереди одним воркером, а модель
**выгружается из RAM при простое** и поднимается обратно по запросу. Принимает
в т.ч. mp3 и mp4 (декодирует ffmpeg). Вся конфигурация — в `.env`, всё
запускается через Docker.

## Состав

| Файл                 | Назначение                                                  |
|----------------------|-------------------------------------------------------------|
| `app.py`             | HTTP-слой (FastAPI: роуты `/gigaam/transcribe`, `/gigaam/health` (legacy aliases `/transcribe`, `/health`))        |
| `transcriber.py`     | поток-воркер: очередь, загрузка/выгрузка модели, инференс  |
| `config.py`          | конфигурация из env (`Settings`-dataclass) + логгер        |
| `schemas.py`         | типы тел ответов API (dataclass'ы для OpenAPI)             |
| `download_model.py`  | разовое скачивание модели с HuggingFace в кеш             |
| `Dockerfile`         | рантайм-образ (onnxruntime + onnx-asr, без torch)         |
| `docker-compose.yml` | сервис + профиль `prepare` (скачивание модели)            |
| `.env.example`       | шаблон настроек                                            |
| `requirements.txt`   | зависимости рантайма                                       |
| `docs/`              | техническая документация (архитектура, API, dataclasses)   |

Подробная техническая документация — в [`docs/`](docs/README.md): как всё
устроено внутри ([architecture](docs/architecture.md)), полное описание
[API](docs/api.md) и [dataclasses](docs/dataclasses.md).

## Быстрый старт

```bash
# 1. настройки
cp .env.example .env        # при желании поправь GIGAAM_MODEL_VERSION, GIGAAM_PORT, GIGAAM_OMP_NUM_THREADS

# 2. разовое скачивание модели с HuggingFace в кеш (./models)
docker compose --profile prepare run --rm prepare

# 3. поднять сервис
docker compose up -d --build
```

Шаг 2 объявлен под профилем `prepare`, поэтому обычным `docker compose up` он не
поднимается — запускается только явной командой (разово, `run --rm`). Он лишь
прогревает кеш, чтобы сервис не качал модель во время первого запроса; можно и
пропустить — тогда модель скачается лениво при первом `/gigaam/transcribe`. Шаг 3
поднимает сам сервис `gigaam`.

Проверка:

```bash
curl -F "file=@sample.wav" http://{host}:{port}/gigaam/transcribe
# {"text": "..."}

curl http://{host}:{port}/gigaam/health
# {"status":"ok","model":"gigaam-v3-ctc","loaded":false,"queue":0}
```

## API

Интерактивная документация поднимается вместе с сервисом:

- **Swagger UI** — `http://localhost:8000/docs`
- **ReDoc** — `http://localhost:8000/redoc`
- **OpenAPI-схема** — `http://localhost:8000/openapi.json`

Типы тел ответов описаны dataclass'ами в `schemas.py` и автоматически попадают
в OpenAPI-схему.

### `POST /gigaam/transcribe`

Распознать речь из аудиофайла.

- **Тело:** `multipart/form-data`, поле `file` — аудиофайл.
- **Принимаемые форматы:** `wav`, `mp3`, `mp4`, `m4a`, `flac`, `ogg`, `opus`,
  `aac`, `webm`, `wma` (декодирует ffmpeg).
- **Ответ `200`** (`TranscribeResponse`):

  ```json
  { "text": "распознанный текст" }
  ```

- **Ошибки:**

  | Код   | Когда                                                        |
  |-------|--------------------------------------------------------------|
  | `415` | неподдерживаемое расширение файла                            |
  | `422` | не передан файл (валидация запроса, добавляет FastAPI)       |
  | `500` | инференс упал                                                |
  | `504` | результат не пришёл за `GIGAAM_REQUEST_TIMEOUT`                      |

  ```bash
  curl -F "file=@sample.wav" http://localhost:8000/gigaam/transcribe
  # {"text": "..."}
  ```

### `GET /gigaam/health`

Состояние сервиса и воркера. Модель не поднимает — годится как healthcheck.

- **Ответ `200`** (`HealthResponse`):

  ```json
  { "status": "ok", "model": "gigaam-v3-ctc", "loaded": false, "queue": 0 }
  ```

  | Поле     | Тип    | Значение                                              |
  |----------|--------|-------------------------------------------------------|
  | `status` | string | всегда `"ok"`, если процесс отвечает                  |
  | `model`  | string | версия модели (`GIGAAM_MODEL_VERSION`)                       |
  | `loaded` | bool   | загружена ли модель в RAM прямо сейчас                |
  | `queue`  | int    | сколько запросов ждёт в очереди воркера               |

## Настройки (.env)

| Переменная        | По умолчанию | Назначение                                      |
|-------------------|--------------|-------------------------------------------------|
| `GIGAAM_MODEL_VERSION`   | `gigaam-v3-ctc` | имя модели для onnx-asr (скачивается с HuggingFace) |
| `GIGAAM_HF_HOME`         | `/app/models`| кеш HuggingFace с весами (том `./models`)       |
| `GIGAAM_TMP_DIR`         | `/app/tmp`   | временная папка для аудио; файл удаляется сразу после распознавания |
| `GIGAAM_IDLE_TTL`        | `60`        | сек простоя до выгрузки модели из RAM           |
| `GIGAAM_REQUEST_TIMEOUT` | `3000`        | макс. ожидание результата (очередь+инференс), сек; дольше — `504` |
| `GIGAAM_CHUNK_SEC`       | `30`         | окно нарезки длинного аудио, сек; `0` — не резать |
| `GIGAAM_CHUNK_BATCH_SIZE`| `8`          | сколько окон гонится одним батчем (выше — быстрее, больше памяти) |
| `GIGAAM_AUDIO_FILTERS`   | `highpass=f=100,dynaudnorm` | аудио-предобработка (цепочка `-af` ffmpeg); пусто — без фильтров |
| `GIGAAM_OMP_NUM_THREADS` | `4`          | потоки CPU для onnxruntime (≈ число физ. ядер)  |
| `GIGAAM_PORT`            | `8000`       | порт на хосте                                   |

> Модели (имена onnx-asr): `gigaam-v3-ctc` (рекомендуется под CPU),
> `gigaam-v3-e2e-ctc` (+ пунктуация и нормализация). `gigaam-v3-rnnt` точнее, но
> на CPU заметно медленнее.
>
> Поменял `GIGAAM_MODEL_VERSION`? Прогони шаг 2 для новой модели (или просто перезапусти
> сервис — скачается лениво), затем `docker compose up -d`.

## Как это работает

- Запросы складываются в очередь (без ограничения по размеру); обрабатывает их
  один поток-воркер, который единолично владеет моделью. Параллельный инференс
  на CPU смысла не имеет, а единоличное владение избавляет от блокировок и гонок.
- Модель не грузится при старте контейнера. Первый запрос поднимает её в RAM
  (cold start — несколько секунд; если модель ещё не в кеше, добавится время на
  скачивание с HuggingFace — поэтому есть шаг `prepare`).
- Инференс — на onnxruntime через библиотеку `onnx-asr`: она сама качает
  ONNX-модель GigaAM с HuggingFace по имени (`GIGAAM_MODEL_VERSION`) и делает
  препроцессинг аудио без torch.
- Тот же воркер выгружает модель из RAM, если запросов не было дольше
  `GIGAAM_IDLE_TTL`. Следующий запрос поднимает её заново.
- Результат не пришёл за `GIGAAM_REQUEST_TIMEOUT` → `504`.
- Аудио декодируется через ffmpeg (моно, 16 кГц). Если задан `GIGAAM_AUDIO_FILTERS` —
  на этом же проходе применяется предобработка (срез гула, выравнивание
  громкости и т.п.), что помогает на тихой/шумной записи.
- Декодированное аудио режется на окна по `GIGAAM_CHUNK_SEC` секунд: энкодер по памяти
  растёт ~квадратично от длины, поэтому длинный файл целиком уводит процесс в
  OOM. Окна обрабатываются батчами и склеиваются в один текст. Минус
  фиксированных окон — слово на стыке может слегка обрезаться; точную нарезку по
  тишине (VAD) можно добавить позже.
- Загруженное аудио пишется во временную папку (`GIGAAM_TMP_DIR`) и **удаляется сразу
  после обработки** — успешной или нет. Сервис ничего не хранит; хранение
  записей и БД живут в отдельном сервисе. Удаляет файл воркер (не HTTP-слой):
  при `504` запрос перестаёт ждать, но файл ещё нужен воркеру до конца декода.

`GIGAAM_WORKERS=1` by default в `Dockerfile` — принципиально: иначе каждый воркер держит свою
копию модели в RAM, и экономия памяти теряется.

> **Без torch.** Инференс и препроцессинг идут через `onnx-asr` на onnxruntime,
> torch/torchaudio в рантайме не нужны — образ заметно легче прежнего.

## Про выгрузку из RAM — что реально происходит

При простое сервис удаляет ONNX-сессии модели и зовёт `gc.collect()`. Веса —
крупные аллокации, в большинстве случаев возвращаются ОС. Остаётся базовый
«хвост» процесса (интерпретатор + библиотеки, ~150–300 МБ). То есть основная
память освобождается, но контейнер не падает в ноль.

Хочешь **гарантированный** возврат всей памяти при простое — инференс выносится
в процесс-воркер, который убивается по таймауту и спавнится по запросу. Это
+немного кода; скажи — допишу.

## Локальный запуск без Docker (опционально)

`app.py` сам подхватит `.env` (через `python-dotenv`):

```bash
pip install -r requirements.txt python-dotenv
# модель скачается с HuggingFace в кеш (GIGAAM_HF_HOME, по умолчанию ~/.cache/huggingface)
python __main__.py
```


Each worker owns its own model copy. Keep `GIGAAM_WORKERS=1` for memory-constrained deployments; budget about 1.5 GiB RAM per worker, plus request buffers. Set the variable to a positive integer to run multiple independent CPU workers.
